# Vibe知识讲解路线

这条路线把现象、词语、谚语或效应做成以连续动画、屏幕文字和声音推动的知识短片。优先让观众愿意看下去，在共鸣、疑惑、反差和发现中理解一个认识。需要系统学会概念或操作时，使用[教学路线](../sop.md)。主题和路线分别选择，AI概念同样可以用Vibe表达。

教学路线由讲解稿与配音承担主要解释，画面帮助演示和理解；本路线由连续画面中的事件、对象关系与结果承担主要解释，字幕补充关键含义、命名概念和点透发现。观众应能从画面认出具体发生了什么，不要求脱离文字猜出准确概念。

默认视频1920×1080、30fps，先制作无人声旁白版本；封面独立为3:4。先编排画面事件与节奏，再结合阅读落实字幕时间，声音克隆不是前置条件。制作分段默认四幕，可按内容调整为1～6段，不为凑幕数或固定时长增加内容。

本路线按“观看推进 → 连续事件与对象关系 → 镜头与视觉重心 → 实际画面验收”四层组织制作，贯穿下面的写稿、时间规划、实现和审片步骤。四层不是四幕，详细标准统一维护在[动态画面要求](motion_design.md)，不新增一套文档或用户审批。

开始、恢复、真实确认及版本处理先读[共用执行规则](../common/execution.md)，路径和脚本位置按[共用登记规则](../common/topic_selection.md)。

新建 Vibe 期次的成片与发布文案默认保存在 `pipeline/output/vibe/epNN_slug/vK/`。使用 `vibe:init`、`vibe:review`、`vibe:mix`、`vibe:publish` 和 `vibe:check-release`；历史期次按[共用输出与兼容](../common/output_paths.md)沿用原位置。

## 从这里开始

用户已经指定路线或主题时直接沿用。用户未指定主题时，AI先按选题规则检查重复，选择一个合适主题，说明选择与讲解角度，再继续；不要每次都要求用户从词表中选择。主题确认和后续具体稿件确认分别记录。

```bash
npm run doctor -- --route vibe
npm run topic:check -- --topic "主题词" --summary "观看入口与讲解角度"
npm run vibe:init -- 03-topic-slug --topic "主题词"
```

查重缺少可选语义Key时沿用[选题规则](../common/topic_selection.md)，如实记录未执行项。初始化建立`route: "vibe"`、`production_contract: "current"`的索引，不能用历史契约或假配音绕过检查。没有`route`字段的已有课程继续使用教学路线；初始化不把旧期次自动切换。

环境需要Node、Python、FFmpeg、Chrome及可用NVENC，与教学路线复用现有渲染依赖。Vibe的doctor只检查Python可运行，不检查VoxCPM、模型或参考声音。按[安装文档](../common/setup.md)准备通用环境；技术链路使用[无人声短示例](../../../examples/vibe-knowledge/README.md)验证。

正式制作开始前还要按[固定配乐](#4-固定背景音乐与混音)确认本地音乐文件已准备；doctor不检查这份音乐，干净仓库也不附带它。技术短示例使用自己的测试音，不代表正式配乐已经就绪。

## 1. 先写观看主线和稿件

写给正在刷短视频的大众：先吸引注意，让人愿意继续看、产生共鸣并愿意点赞或分享，在观看中自然理解一个概念。创作先问“这件事有什么值得讲、怎样讲让人想往下看”，不以覆盖全部知识或形成可复述的课堂答案为目标。

先从资料和生活观察中挑出有代入感的处境、有意思的事件、鲜明的反差或可想象的意象，确定观看入口与主要发现，再组织成完整稿。已有观看主线简记开场的期待、展开怎样带来变化、结尾留下什么感受或认识即可。开场按[前三秒的观看理由](motion_design.md#前三秒的观看理由)先让观众接触具体处境或变化，后文接住这份期待，不用无关片头消耗开头。写稿时同步考虑哪些意思由可见事件、关系和结果表达，哪些需要文字点明，不先把正文写成独立讲完所有内容的配音稿再逐句配图；此时不要求完成分镜或动画。内容需要解释时，优先让具体动作、对象关系和结果承载解释；首次主题登场按[点题时间](motion_design.md#首次点题时间)留出位置，不机械先讲完定义再开始故事。

主线统一不等于例子统一。同一个人物或物件可以贯穿全片，只要经历、关系或观看范围继续发展；也可以换故事、研究或视角，共同推动对同一个问题的认识。推进可以是新事件、新理解、反差或情绪变化，必要铺垫、留白和回响也有作用；不要求每句都加新信息，不规定案例、研究、反转或高潮的数量。换场景却仍反复解释同一结论时，应压缩或重组选材。

语言要好懂、有画面、有节奏。允许比喻、拟人、夸张和有感染力的概括，把抽象关系写成观众能想象的经历；不把修辞逐字当成科学命题，也不为保险逐句补“可能”“未必”。基本事实和核心含义仍须可靠：实际采用的研究、数字和引语核对来源，不虚构实验或更改结果；确实改变观众理解的限定融入正文，其余细节留在资料备注。核验用于纠正实质错误，不要求把研究条件、争论与全部边界讲进视频。

结尾从前文形成的意象、期待或矛盾中收束，可以留下新的看法、情绪或问题，也可以给出观众此时需要的办法。建议和直接提醒本身不等于说教；看它是否回应前文，而非突然站出来教育观众。不强制总结、安慰、励志或回到原场景，也不靠末句金句补救整篇缺少推进。

### 正文衔接与参考写法

用户提供或项目已有可用的参考纯旁白时，先完整阅读，理解它为什么让人停下、继续看并留下感受：选了什么材料，怎样安排发现，语言怎样形成画面，节奏怎样变化，结尾怎样获得前文支撑。学习整篇的创作选择，再用于本期；不只摘一句结尾或检查相邻连接词。参考不是固定结构，不把它的年份排列、实验数量、建议段或句式变成每期要求；引用其中事实时仍核对来源。没有参考也可直接创作，不新增外部查阅依赖。

转场可以承接疑问、建立期待、形成反差或唤起前文。“回到”“更离谱的是”“有意思的是”和必要编号都结合后文判断，兑现了期待就有作用；只报段落位置或空喊惊人而没有内容时再删改。重复也可以形成铺垫、强调和回响；重点是再次出现时有没有新的含义或感受，不按词语或重复次数判退。

文字密度由内容与画面共同决定。有的段落靠文字连续揭示，有的让动作展开并保留无字幕时间；不从某条参考推导全片统一字数或读速，不让文字复述画面已经清楚表达的每个细节。画面要解释的名称和正文覆盖仍按后续字幕与标注规则落实。

### 切分前的主线审查

完整初稿形成后，先从观众角度通读：哪里想继续看，哪里难懂、重复或失去兴趣，结尾有没有接住前文。再集中处理实际采用内容的事实、因果与指代问题，按[共同事实核验与单次润色](../common/script_content_review.md)执行一次润色；本路线保留已审查的实际分段与观看问题，增强画面感、反差及情绪感染力，不补成固定四幕或按知识覆盖表判退，不逐句要求证明修辞，也不机械套用技能的逐项举证、专家评分或循环复审。修改后连读受影响部分及前后接点即可，不另起多轮完整审查。

开场没有观看理由、展开持续重述同一意思、关键解释让人无法理解，或结尾与前文脱节时，先修选材与组织，再进入切分。若问题跨越整幕，应重排相应内容，不能只替换末句或增加过渡语。必要停留和有意义的回响可以保留；资料完整、措辞保险、技术检查通过均不能替代观看体验。后续画面按[结尾收束](motion_design.md#结尾收束)兑现正文建立的联系。

在已有`content_review`或审查记录中简记整体结论、实际发现的问题和处理结果，问题定位到具体句段；没有问题时简记结论即可。不逐段撰写“通过证明”，不另列情绪评分、参考分析表或新增审批。修辞不因无法逐字证明而判退，事实核验与修改保留必要来源依据。正文可读、观看主线成立且实质问题处理后，进入下面的切分与既有内容确认。

具体改稿先给用户确认，再改文件。讲解稿、切分预览和实际字幕须覆盖相同原文；原文标点保留到时间表，仅在最终显示时去掉，不能因此删句、改词或让道具标签取代完整文字。完整覆盖不等于整句必须同屏；完整问句优先保留语义，长句按[主字幕长度与分屏](motion_design.md#主字幕长度与分屏)处理，不因短句偏好硬拆。

先填写制作索引的`script`与`split_preview`真实路径。正式稿使用`## 第一幕`至实际末幕及`旁白：...`正文格式；`旁白切分预览.json`使用`{"act1":["原文句组"],"act2":["原文句组"]}`，按实际1～6幕连续编号，句组保留原文标点。这份文件用于核对正文语义段，一段可以含多句话，不能将它当作逐屏字幕交付。正式稿放在`course/scripts/`，切分与索引放在`course/episodes/NN-slug/`。

### 程序初切与人工复核

正文审查通过、上述两份文件一致后，运行Vibe专用程序初切，不使用教学36字符及配音短句合并的默认输出：

```bash
npm run split:vibe -- course/episodes/03-topic-slug/制作索引.json
```

命令在本期索引同目录生成`字幕初切草稿.json`，按幕列出`source_text`、每屏`captions`及`review_notes`，保留标点；`start`、`end`、`total_s`均为`null`，不按字数自动排成片时间，也不生成TTS字段或用户确认。程序复用已有标点与成对引号断句能力，按Vibe字数口径组合分句，短句只在当前句内合并；完整问句尽量保持联系，数字分组、时间及引号内的专名不按内部逗号硬切。程序不能识别所有专名或语义，不能因此省略人工复核。

退出码`0`表示初切完成且没有长度等专项提示，不表示人工复核通过；`3`表示草稿已生成但有待处理提示，须逐项检查；`1`表示执行失败。15～18字需检查保留理由，19～24字需检查必要双行或继续分屏；超过24字且没有安全断点的内容保留原文并明确报错项，不截断专名、不删词。相同输入可重复运行；现存草稿与新结果不同时拒绝覆盖，改用`--out course/episodes/03-topic-slug/字幕初切草稿-v2.json`另存，不覆盖人工修改。

此处先复核句意、指代、完整问句、专名与单位，保留生成依据；初切及复核结果仍是可调整草稿，不据此锁定屏数、动作边界或整片时长。第2步先编排连续画面，再结合实际动作与阅读窗口调整断点和起止时间，形成统一的`captions`；动画与逐屏预览均读取这份时间表，不能在动画脚本再维护另一套文字数组。初切与人工复核分别如实记录；从人工数组导出文件不等于运行过程序初切。

沿用既有内容和切分确认节点，向用户说明交付的是语义段、初切草稿还是已复核逐屏字幕。用户索要“字幕切分”时，交付每条对应一屏的文件；时间表尚未生成时可交付明确标注状态的初切草稿，不能只给正文段落预览。用户确认后，助手记录`content_approval: {"confirmed": true, "statement": "用户原话"}`；调整涉及改词、增删正文时，仍先按原要求确认，不增加审批节点。

内容与切分确认完成后执行一次版本绑定，此时不需要画面或时间表：

```bash
npm run timeline:vibe -- course/episodes/03-topic-slug/制作索引.json --bind-approved-source
```

命令先核对正式稿与预览，再保存`content_approval.source_sha256`，记录本次认可的各幕正文及切分版本；它不创建用户确认。原文或切分变化后，普通时间表、review和发布检查会拒绝旧绑定，须先按已有改稿确认流程处理再更新绑定，不能用此参数直接消除未确认改稿的报错。更新正文绑定会使旧的整片审片和发布确认失效；相同版本重复绑定保留已有确认。已确认的旧期次可在核实现存文本确为认可版本后补绑定，不重复索取未变化内容的确认。技术示例使用`example.technical_only`明确跳过真实正文确认绑定，不用它绕过正式制作检查。

这里绑定的切分版本是`split_preview`所指的语义预览。后续只调整逐屏断点、换行或时间且不改变正文及语义预览时，不重绑正文或重复索取内容确认；更新实际时间表、逐屏预览及受影响画面后，按原审片范围复核。

## 2. 先编排连续画面，再落实字幕与时间

### 连续事件与节奏先行

先按[画面编排文件](visual_methods.md#本期画面编排文件)建立本期唯一的《画面编排.md》，由制作索引顶层`visual_plan`指向真实路径。先写全片观看安排与幕间接续，再展开当前幕；这是本期制作产物，不新增审批。当前幕的过程未写清前，不进入逐屏定时或动画实现。

编排时查看[20种风格素材库](../../../examples/vibe-styles/README.md)中与本段任务相符的完整动态示例，按需直接复用绘制与动效源码，保留有效的材质、光影和运动细节，再调整为本期对象与接续。素材选择由AI结合内容和已有风格确认完成，不新增逐项选风格的用户门禁。准备、时间轴接入及验证范围按素材库说明执行；原例小字、演示题材、十秒时长及完整构图不作为生产标准，具体制作和验收仍按下面四层执行。

先按本幕相邻讲解任务，使用[画面组织与动效方法](visual_methods.md)，明确主体、观看范围或对象关系怎样发展，再决定用什么动作呈现，按[动态画面要求](motion_design.md)落实四层。方法直接对应本期对象、起点、触发、中途状态、结果与下一段接点，不照搬固定分镜；AI按内容选择并沿用已有风格确认，不要求用户逐项选方法。不能只登记风格名称，或从固定布局直接开始堆局部动效：

| 层 | 要落实的事 | 使用已有产物 |
|---|---|---|
| [观看推进](motion_design.md#第一层观看推进) | 本段接住什么期待，产生什么发现或情绪变化，如何回应前文 | 观看主线、正文及内容审查记录 |
| [连续事件与对象关系](motion_design.md#第二层连续事件与对象关系) | 按讲解任务组织主体、范围与表达方式，连接触发、过程和结果；长段有持续发展 | 《画面编排.md》的当前幕，包含本期对象、状态变化及相邻任务的接续 |
| [镜头与视觉重心](motion_design.md#第三层镜头与视觉重心) | 主次随事件变化，必要解释靠近主体、随动作出现；镜头兑现信息任务 | 《画面编排.md》中的镜头与标注设计、实际画面源码 |
| [实际画面验收](visual_review.md) | 连续复查整幕和相邻接点，分别判断结构发展、动作解释、视觉表现及技术结果 | 实际片段、制作索引或已有验收记录 |

画面编排进入实现前，按[画面编排与持续发展](motion_design.md#画面编排与持续发展)连续核对相邻任务：谁接管主体、观看范围或关系怎样发展、结果如何引出下一段。仅在固定布局轮流加卡片、图标或高亮而未兑现任务变化时，退回编排；不能只因局部动作已写齐而放行。结尾按[结尾收束](motion_design.md#结尾收束)在本期《画面编排.md》中说明承接状态、可见结果与最后构图的联系，再进入实现。字幕不变时也可以丰富对应动作，但不为填空增加无关动作。局部返工和复用前按第四层核对既有反馈与验收状态，保留有效部分及其他未解决项。

当前幕编排经助手自查成立后，再据此确定事件、揭示和接续的大致节奏，并考虑必要文字的阅读空间；不逐条按初切字幕分配场景和秒数。画面编排尚未成立时，不能进入逐屏定时；已有总时长和分屏数量也只能作为待验证草案。

### 配合画面落实字幕与时间

根据上述编排粗排全片的动作、揭示、阅读与停留时间，检查是否过长、重复或主题出现太晚；在制作索引的`topic_reveal`填写`start_s`与`complete_s`，均为相对正片0秒的累计秒数；开始不得晚于完成，完成必须在16～19秒内（含边界）且不超出整片。按[首次点题时间](motion_design.md#首次点题时间)编排后再逐幕实现并审看，程序将这两个时刻原样导出到整期时间表。四幕总时长是本期设计结果，不以每句字数、参考片重拍点或TTS读完速度机械决定。

场景、镜头和视觉阶段不设统一最短时长；首次点题的16～19秒窗口及[展示完成后的1秒阅读停留](motion_design.md#知识点展示后的阅读停留)分别按专门规则执行，不推成镜头时长下限。除此以外，额外时长限制只设上限，并按[时长与计时口径](motion_design.md#时长只设上限)在已有时间表说明约束对象及连续起止，不把换字幕或局部高亮当作重新计时。没有确认依据时不自行添加统一场景秒数阈值。

讲解不必铺满时间轴。字幕可以在仍有阅读或情绪作用时保留，也可以清除，让动画独立推进情境、动作或关系；未来加入人声也允许无讲解的空段。前文提前讲完而点题窗口未到时，应由有内容发展的画面承接，不冻结旧字幕、慢放或循环凑秒数；这一原则适用于全片。字幕之间留空不等于漏稿，已确认正文仍须完整覆盖。

将初切草稿与连续事件对照，调整字幕断点、出现时机及阅读窗口，再按幕保存画面时间表，填写本轮计划的`total_s`及每屏`start/end`，复核提示的处理理由留在已有记录中。一句字幕可以跨多个动作，一个连续事件可以承接多屏字幕，换字幕不指挥换场景。若动作已经完成而文字尚未读完，先检查提前呈现、跨后续相关动作阅读或重分屏是否合适，也可保留有理解或情绪作用的停留；不拉长无进展的旋转、推近或循环来凑时长。若读字与关键动作争夺注意力，应调整事件安排与阅读窗口，不能将字幕快闪塞进动画；涉及改词、增删正文时仍先确认。时间未确定的`null`不能进入渲染。索引填写`acts[].visual_timing`，不是TTS timings；以下仅展示时间表结构，不是固定分屏模板：

```json
{
  "total_s": 8,
  "source_text": "这些投入收不回来。未来的时间还能选择。",
  "captions": [
    {"id": "c01", "start": 0, "end": 4, "text": "这些投入收不回来。"},
    {"id": "c02", "start": 4, "end": 8, "text": "未来的时间还能选择。", "emphasis": ["时间"]}
  ]
}
```

字幕必须能读完，时段不重叠且不超出本幕；拼接字幕去掉标点和空白后须与`source_text`一致。重点放在具体词上，只强调必要的词，每幕通常不超过三个，不要求每句着色。源码的`const DUR`和根`data-duration`与`total_s`一致。

时间表的`captions`应落实实际逐屏显示：先按保留标点的原文确定分屏，再填写各屏真实起止时间，最后显示时去标点；切分预览的一条可以对应多条时间表字幕，显示层按时间表逐屏切换。分屏顺序、单屏长度、双行条件和实际画面验收统一按[主字幕规范](motion_design.md#主字幕长度与分屏)执行，不把较长的讲解稿语义组直接当作必须整句同屏的字幕。

准备所有时间表并登记`topic_reveal`后执行：

```bash
npm run timeline:vibe -- course/episodes/03-topic-slug/制作索引.json
```

正式视频缺少`topic_reveal`、登记值越界或时间顺序错误时，时间表导出明确失败；`review`、`publish:package`及独立`check:release`还核对索引与整期时间表的点题值一致。旧期次重新制作或发布时须补充真实记录；不自动填成17秒。仅已有`example.technical_only`技术短示例沿用豁免，不代表正式视频通过。程序只检查登记数据，名称何时真正完整可读须按[画面验收](visual_review.md)核实。

命令对照已绑定的正式稿、语义预览与各幕`source_text`，校验字幕覆盖、时段及同屏最多24字，再从同一组`captions`生成连续的`整期时间表.json`与`逐屏字幕预览.json`，登记索引的`timeline_summary`、`caption_preview`和总时长。逐屏预览仍用`act1`等数组保存，每条恰好对应一屏，顺序、文字和标点与实际时间表一致；语义预览与逐屏预览必须使用不同文件路径。

连续小样及整幕审看中的时间或断点变化后重跑该命令，不手改导出的预览，也不沿用旧边界。review和发布检查会逐条核对已登记的逐屏预览，仅全文拼接相等但屏数或断点不同仍须重新导出。未登记该字段的历史索引保留兼容，重新制作时运行时间表入口即可补齐。字数和导出检查不代替每行长度、实际显示是否累计旧字、阅读时间与画面主次，具体按[字幕规范](motion_design.md#主字幕长度与分屏)执行。

## 3. 逐幕实现与连续审看

实现前读取索引`visual_plan`对应的当前编排，按第2步形成的连续事件、字幕与时间安排进入实现；实际小样发现节奏或阅读冲突时，联动调整受影响的编排、字幕断点和时间，再重新导出预览，不把粗排时长当成不可变约束。

主题登场按[主题登场与特效选择](motion_design.md#主题登场与特效选择)结合本期知识点、具体旁白及前后画面设计，保留有效的呈现方式并加强揭示瞬间；不套用固定特效模板或复制已认可小样。选效依据落实到本期编排；知识点主视觉按[阅读停留规则](motion_design.md#知识点展示后的阅读停留)在完整落定后保留1秒。编排时安排阅读窗口，时间表记录完成、停留结束与接续时刻，实现时保持重点可读，交付前核对实际视频，不能只按代码时长判定通过。

制作时对照编排实现主体过程及任务接续，按[动作表现方法](motion_design.md#动作怎样产生表现力)安排起动、响应、速度和落定，并按[动作标注与解释](motion_design.md#动作标注与解释)让必要名称、数字和解释贴近对应主体、随动作同步。按[方法实施要求](visual_methods.md#接入当前制作方式)用本期内容和实际整幕源码先做连续小样；在已有验收记录中对照计划中的状态与结果，检查任务转换、动作力度、标注移动中途和缩小状态。若只实现了局部动画而未实现组织变化，修实现或退回编排，不用新增装饰、切镜或运镜替代，也不先批量扩展同一未验证方案。小样需要调整时间时回到第2节同步时间表及预览，不强行拉伸装饰动作凑字幕时间。

背景基调默认继承[深蓝或蓝绿暗底](motion_design.md#背景也参与表达)，本期各幕及后续各期直接沿用，不再每期重新询问浅色还是暗色；用户明确指定其他方向时再调整。其余配色、字体、形象、材质与运动感觉按本期内容设计，已有确认继续有效，新的视觉方向仍沿用既有风格确认节点及实际画面审看。Vibe不强制使用教学A/B/C固定开场或视频章节覆盖栏。各幕仍要共享视觉语言，具体环境随内容改变。

文字按已确认的[手机观看字号](motion_design.md#手机观看字号)制作：1920×1080基准下，主字幕80px，观众必须读清的场景文字至少64px；仅表现有字而无需阅读的细节可更小。编排时区分文字用途，实现及审片时检查阅读时段内缩放后的实际大小；空间不足先调整分屏、构图或必要双行，不缩字塞入。字体风格可随本期设计，字号标准直接沿用，不重复询问。

画面源保存在`course/acts/epNN_slug/`，索引填写`visual_source`、`visual_assets`及可选`sfx`。实现前读取[共用 HTML、素材与确定性契约](../common/visual_contract.md)。本路线根画幅按本节规格，DUR 与 visual_timing.total_s 对齐；主字幕使用时间表导出的 SUBS，在稳定阅读区显示。制作中执行[共用视觉检查](../common/visual_review.md)，路线专属语义和表现仍按下方 Vibe 验收执行。

动作声可以是单声道或立体声。没有动作声的分段让`sfx`为空，渲染器使用实际静音音轨完成拼接；它不是伪造配音，也不会填入`audio`或`timings`。布局声明、首现和媒体检查按[共同渲染验收](../common/render_verification.md)。

```bash
npm run vibe:review -- course/episodes/03-topic-slug/制作索引.json --act 1 --check-only
npm run vibe:review -- course/episodes/03-topic-slug/制作索引.json --act 1 --range 0:6
npm run vibe:review -- course/episodes/03-topic-slug/制作索引.json --act 1
npm run vibe:review -- course/episodes/03-topic-slug/制作索引.json
```

Vibe审片直接输出high质量；资源、局部预览和缓存按[共同渲染规范](../common/render_verification.md)，本节只规定路线交付顺序。每次交付对应视频、正式稿及索引`caption_preview`所指的逐屏字幕路径，注明版本与范围；需要解释正文结构时另给语义预览并标明用途。按用户安排逐幕审看，合并前检查全局起伏与所有幕间接点。

交付前按[Vibe实际画面验收](visual_review.md)对照正文、《画面编排.md》与实际视频，连续复查整幕及相邻接点，并在正常速度、约360～480px宽的实际MP4中核对动作与解释能否同时看懂。结构停滞、任务变化或视觉表现未兑现、结尾结果未完成收束、必要标注遮挡或读不清时必须返工，具体起止和原因记入已有验收记录；技术检查通过或最新局部修好不能抵消这些失败，也不新增用户审批节点。

## 4. 固定背景音乐与混音

动作声对应具体可见动作，切镜头不自动加沙沙声。先选音色，再检查音量、落点和密度。音乐、人声与动作声分别处理；先完成无人声版本，可选人声在成片后再讨论。需要精确踩音乐时提前确定素材和片段，后加音乐不声称已经按音乐重拍制作。

Vibe系列固定使用《千年之后》氛围版试听音乐，项目内的固定本地路径为`.local/music/千年之后_氛围版_试听.mp3`。背景音乐增益固定为`0.25`（25%），动作声增益保持`1`（100%）；这是用户已确认的系列设置，后续每期直接沿用，不重复选曲或询问比例。用户明确要求更换音乐或调整比例时，才处理对应变更。

首次配置将这份音乐放入上述位置；该目录已被Git忽略，音乐不随仓库提交。文件缺失或损坏时明确报告并补齐同一素材，不静默换曲。音乐是背景配乐，不生成旁白人声，也不触发声音克隆。

音乐始终从正片0秒开始，随视频结束。先用`ffprobe`读取无BGM底片的实际时长：音乐够长时直接使用固定原文件；不够长时，从头循环同一首到覆盖底片全长，生成本期的循环音轨，不换曲、不留无配乐的尾段。例如在仓库根目录执行，替换底片、期次、版本及实测秒数：

```bash
ffprobe -v error -show_entries format=duration -of default=noprint_wrappers=1:nokey=1 "底片.mp4"
ffmpeg -hide_banner -y -stream_loop -1 \
  -i ".local/music/千年之后_氛围版_试听.mp3" \
  -t "底片实测时长秒数" -map 0:a:0 -vn \
  -c:a pcm_s16le -ar 48000 -ac 2 \
  "course/episodes/03-topic-slug/bgm-loop-vK.wav"
```

循环只是重复原音乐，不自动做淡入淡出、交叉淡化或归一化。准备后复核音轨时长、循环接点和全轨解码；底片变长后重新核对，不能沿用较短的旧循环文件。保留固定原音乐及已确认版本，循环产物按本期版本另存。

在制作索引填写已确认的系列默认设置；`bgm.file`在原音乐够长时指向固定文件，生成循环音轨后改填本期真实的循环文件路径。以下是正式默认值，不是待试听的候选比例：

```json
"bgm": {
  "file": ".local/music/千年之后_氛围版_试听.mp3",
  "source_gain": 1,
  "gain": 0.25,
  "approval": {
    "confirmed": true,
    "statement": "每次都是固定用这个。这个就是固定的背景音乐，就是不断重复，如果说他的背景音乐不够的话音量比例就是背景音乐25%。"
  }
}
```

已有系列确认可以沿用，不要求每期重新试听批准配乐；完整最终视频仍须按原审片节点确认。只有用户要求试听或调整时，才生成分轨试听页：

```bash
npm run vibe:preview-music -- course/episodes/03-topic-slug/制作索引.json
```

试听页引用未混音乐的`review_base_output`，避免双重叠加；暂停和拖动时音乐同步。先准备够长的原音乐或循环音轨，再打开试听。页面上的滑杆或上次浏览器保存值不自动改变正式索引；用户明确要求的新比例才更新对应设置。所有增益均为线性比例，不自动归一化、压低原声或加淡入淡出。

```bash
npm run vibe:mix -- course/episodes/03-topic-slug/制作索引.json
```

命令复制视频编码数据，另存配乐版并检查解码、声道、起止、时长和削波，保留底片与原音乐。先核验临时候选，通过后才替换输出；失败不覆盖已有配乐版。混音版更新`review_output`，需要审看这份完整最终视频；默认配乐未完成时，不将无BGM底片视为完整最终视频。

完整review始终写当前版本的无BGM底片，不把配乐路径当作画面输出。重建画面或改变混音后，旧发布验收状态失效；未变化的混音文件保留已有确认。已确认内容需要修改时另存新版本，复用未改动的媒体，再执行受影响阶段。

## 5. 独立封面与发布文案

进入本步读取[独立封面制作与验收](cover_workflow.md)：先确定中心主题及整张海报的视觉创意，再按实际能力选择AI生图或代码制图；缺少生图能力时直接代码生成。两条路径都交付项目内的实际3:4图片，说明采用方式与原因，完成审美和规格检查，再按已有节点取得用户确认。封面可以使用独立于正片内容的视觉表达，不强制搬用正文道具；详细设计、提示词、出图、保存与返工标准统一由该文档维护。

发布TXT仍包含标题、发布文案、标签、视频总结、视频章节，顺序与[发布交付](../common/release_delivery.md)一致。Vibe专属规则：

- 标题为`Vibe知识大赏｜主题词：短问题或反差`，冒号后含标点最多15个字符，通常10～12个汉字即可，不为凑长度加词。
- 正文简短展开同一个矛盾，结尾保留一个有力的问题，避免重复反问。只改发布文案不自动改讲解稿或视频。
- 标签包含`#Vibe知识大赏`及与主题相关的标签；不强制`#AI基础`或`#深度讲解`。
- 总结内容解释核心认识和必要边界；长度、禁用内容及独立性按[共同文案格式](../common/release_delivery.md#二发布文案格式)。
- 发布章节按[共同章节规则](../common/release_delivery.md#三章节标题与时间)生成；不要求视频覆盖栏。

## 6. 确认高清审片版，生成并验收发布包

完整最终视频获用户确认后，助手在`review_approval`保存`confirmed: true`、用户原话与该文件的SHA256。发布入口拒绝确认后变动的文件；示例例外只表示技术核验，不创建用户认可。

```bash
npm run vibe:publish -- course/episodes/03-topic-slug/制作索引.json
```

发布入口直接复制已确认的high审片版，将选定的独立封面复制为同目录`cover.png`，保留同版文案，并执行路线发布检查。它核对文件、版本、规格、时长、章节、文案、音轨一致、3:4封面和台账；不要求片尾静音或首帧嵌入封面。通过后保存`release-check.json`，真实登记`publish_bundle.complete`。

修改文案、封面或索引后独立复查：

```bash
npm run vibe:check-release -- course/episodes/03-topic-slug/制作索引.json
```

新期次输出在`pipeline/output/vibe/epNN_slug/vK/`；历史目录兼容按共用输出规则。公开上传须按用户授权另行执行，不把本地交付写成已公开发布。生成视频、用户声音、音乐、模型、密钥和个人路径继续本地忽略；生产规则和通用工具随仓库分发。

## 7. 发布后的重建输入

按[Vibe重建输入](published_cleanup.md)核对画面、动作声、音乐及确认原件，删除条件只执行[共同清理规范](../common/published_cleanup.md)，不按版本号整目录删除。
