# Vibe知识讲解路线

这条路线把现象、词语、谚语或效应做成以连续动画、屏幕文字和声音推动的知识短片。优先让观众愿意看下去，在共鸣、疑惑、反差和发现中理解一个认识。需要系统学会概念或操作时，使用[教学路线](../sop.md)。主题和路线分别选择，AI概念同样可以用Vibe表达。

默认视频1920×1080、30fps，先制作无人声旁白版本；封面独立为3:4。画面与文字阅读决定时间，声音克隆不是前置条件。制作分段默认四幕，可按内容调整为1～6段，不为凑幕数或固定时长增加内容。

本路线按“观看推进 → 连续事件与对象关系 → 镜头与视觉重心 → 实际画面验收”四层组织制作，贯穿下面的写稿、时间规划、实现和审片步骤。四层不是四幕，详细标准统一维护在[动态画面要求](motion_design.md)，不新增一套文档或用户审批。

## 从这里开始

用户已经指定路线或主题时直接沿用。用户未指定主题时，AI先按选题规则检查重复，选择一个合适主题，说明选择与讲解角度，再继续；不要每次都要求用户从词表中选择。主题确认和后续具体稿件确认分别记录。

```bash
npm run doctor -- --route vibe
npm run topic:check -- --topic "主题词" --summary "观看入口与讲解角度"
npm run init:episode -- 03-topic-slug --topic "主题词" --route vibe
```

查重缺少可选语义Key时沿用[选题规则](../common/topic_selection.md)，如实记录未执行项。初始化建立`route: "vibe"`、`production_contract: "current"`的索引，不能用历史契约或假配音绕过检查。没有`route`字段的已有课程继续使用教学路线；初始化不把旧期次自动切换。

环境需要Node、Python、FFmpeg、Chrome及可用NVENC，与教学路线复用现有渲染依赖。Vibe的doctor只检查Python可运行，不检查VoxCPM、模型或参考声音。按[安装文档](../common/setup.md)准备通用环境即可。

正式制作开始前还要按[固定配乐](#4-固定背景音乐与混音)确认本地音乐文件已准备；doctor不检查这份音乐，干净仓库也不附带它。技术短示例使用自己的测试音，不代表正式配乐已经就绪。

## 1. 先写观看主线和稿件

先说明观众为什么停下、期待看到什么、哪一处产生发现，以及最后希望观众留下什么感受或认识。结尾怎样接住开场的具体处境、疑惑与情绪，要写进已有观看主线，不能只写“总结概念”。情绪锚点可以是舍不得、失控或误解，道具不必贯穿全片。通常从具体处境、问题或反常现象进入，在开场稿件中为首次主题登场留出位置，时间及完成判定按[首次点题时间](motion_design.md#首次点题时间)执行。

表达以通俗、吸引注意和容易理解为先，保留必要事实和因果关系，不要求像科研报告一样展开所有细节。资料核验负责确认准确性，是否写入正文还要判断它能否推进本期观看问题；与主题相关不等于必须讲。限制条件只有在省略会让观众实质误解当前主张时才进入正文，并尽量融入解释；其余研究争论与细节留在资料备注。不为反驳正文没有提出的绝对结论，提前打断尚未讲清的核心过程。

引用研究先核实原始条件、人数与结果，再用观众听得懂的选择和结果改写；不添加没核实的倍数或把问卷选择写成真实投资。一个生活例子可以建立代入，另一个例子或研究提供反差，但都须服务观众正在经历的疑惑。结尾可以通过理解、释然、惋惜、惊讶或关系变化收束，也可以形成新的认识；不要求每期给判断准则、行动建议或概念总结。需要方法时，让它回应前文形成的具体需要。感受应由内容自然形成，不能为安慰或煽情扩大事实结论。

### 正文衔接与参考写法

用户提供或项目已有可用的参考纯旁白时，写稿前先通读正文，观察相邻句怎样接上、反差怎样继续、结尾怎样回应开场。提炼其中的因果、动作结果、对比或具体原话回扣，用于本期内容；不照搬句子、固定结构或未经核实的研究说法，也不因为两条参考采用了某种写法就要求每期套用。

正文优先让具体的人、物、动作和问题继续发展。转场句应帮助理解内容，不能只报告“现在讲到哪里”或重复提醒观众换场景；幕名、镜头与场景调度留在画面说明中。不要每期用同一种转场句式只替换对象，也不能把“回到”换成“再看”就算完成修改。回扣前文时，要唤起具体原话、动作或处境，并在后文产生新的解释、关系或情绪；不按某个词一律判定好坏。

在既有单次润色和连续顺读中检查自然衔接，不增加另一套改写技能或审批：隐藏幕名、场景标注及画面说明，只读正文；标出仅起导航作用的句子。删去后若内容、指代与观看期待均完整，且前后更自然，就删除；若因此暴露断裂，应改前后句的关系，不能再加一句同义导航来遮住。普通连接词、必要定位和有效回扣可以保留，不为追求短句强行删除。

参考写法及采用效果简记在现有内容审查记录中，用实际相邻句说明判断。不另建参考分析稿；不能只写“无AI味”或“口语自然”就认定通过。具体正文改写仍遵守下方已有确认要求。

### 切分前的主线审查

复用[内容审查与润色](../common/script_content_review.md)中的事实核验、因果与指代、连续顺读及单次`copy-editing`润色。Vibe的主干是本期观看问题与发现，不要求覆盖资料的全部分类，也不套用教学的固定点题句、四幕结构和TTS切分要求。除此之外，必须对照实际正文完成以下检查：

- 开场让观众期待接下来看到什么，正文是否建立了具体疑惑、矛盾或反常之处；不要求必须用问句。
- 逐段说明上一段留下了什么期待、本段带来什么新理解或必要的情绪推进、下一段为什么接在这里。只重复结论、罗列资料或讨论旁支而不推进观看问题的段落，应删除或调整。
- 核心问题是否真正得到回应，需要说明“为什么”或“怎样发生”时，是否讲清了过程；不能用概念名称、研究结果或适用条件代替本期需要的核心解释。
- 末幕怎样承接开场的具体处境与情绪，观众最后留下的感受或认识由哪些正文关系形成；认知结论是否准确、情绪期待是否得到回应分别核对，不能用前者代替后者，也不强制所有主题都以释然结束。
- 从末幕开头连续顺读到结束，研究、机制和反差是否继续服务观众的疑惑，讲述姿态是否突然变成替概念发言、评价或告诫观众。能解释一个道理，不等于本期末幕已经完成；不能只检查最后一句是否有关联。
- 隐去幕名与画面说明后，相邻正文是否仍自然相接；转场是否提供必要指代、内容推进或有效回扣，是否只是套用导航句。发现模板式衔接时，须定位原句并删除或改写，主线成立不能替代这一检查。

在现有制作索引的`content_review`或已有审查记录中保存结论及正文依据，标明场景或具体句子；末幕分别说明认知依据、情绪接续与讲述姿态，不只复述稿前主线或以“承接成立”概括通过。任一项不满足，整稿判定不通过，写明位置、缺少的推进及返工方向，修改后重审；事实准确、资料覆盖、可解析性和字幕一致性通过，都不能抵消主线失败。通过后再做单次润色，并按同一标准复核，全部通过才进入切分预览和既有内容确认，不增加审批节点。

若问题出在末幕的信息安排或叙事任务，应重排受影响的整幕，可以保留有效事实，不把返工缩成末句同义替换。将“提醒我们”换成“告诉我们”，或在总结后追加“所以别给自己太大压力”，均不能自行证明情绪收束成立；这些词也不是一律禁用，须判断具体上下文。稿件审查不能仅凭画面说明里的“回到聊天”“人物释然”补过正文缺失的联系；画面编排还须按[结尾收束](motion_design.md#结尾收束)兑现过程，不要求每期回到原场景、安慰观众或励志升华。

具体改稿先给用户确认，再改文件。讲解稿、切分预览和实际字幕须覆盖相同原文；原文标点保留到时间表，仅在最终显示时去掉，不能因此删句、改词或让道具标签取代完整文字。完整覆盖不等于整句必须同屏；完整问句优先保留语义，长句按[主字幕长度与分屏](motion_design.md#主字幕长度与分屏)处理，不因短句偏好硬拆。

先填写制作索引的`script`与`split_preview`真实路径。正式稿使用`## 第一幕`至实际末幕及`旁白：...`正文格式；`旁白切分预览.json`使用`{"act1":["原文句组"],"act2":["原文句组"]}`，按实际1～6幕连续编号，句组保留原文标点。这份文件用于核对正文语义段，一段可以含多句话，不能将它当作逐屏字幕交付。正式稿放在`course/scripts/`，切分与索引放在`course/episodes/NN-slug/`。

### 程序初切与人工复核

正文审查通过、上述两份文件一致后，运行Vibe专用程序初切，不使用教学36字符及配音短句合并的默认输出：

```bash
npm run split:vibe -- course/episodes/03-topic-slug/制作索引.json
```

命令在本期索引同目录生成`字幕初切草稿.json`，按幕列出`source_text`、每屏`captions`及`review_notes`，保留标点；`start`、`end`、`total_s`均为`null`，不按字数自动排成片时间，也不生成TTS字段或用户确认。程序复用已有标点与成对引号断句能力，按Vibe字数口径组合分句，短句只在当前句内合并；完整问句尽量保持联系，数字分组、时间及引号内的专名不按内部逗号硬切。程序不能识别所有专名或语义，不能因此省略人工复核。

退出码`0`表示初切完成且没有长度等专项提示，不表示人工复核通过；`3`表示草稿已生成但有待处理提示，须逐项检查；`1`表示执行失败。15～18字需检查保留理由，19～24字需检查必要双行或继续分屏；超过24字且没有安全断点的内容保留原文并明确报错项，不截断专名、不删词。相同输入可重复运行；现存草稿与新结果不同时拒绝覆盖，改用`--out course/episodes/03-topic-slug/字幕初切草稿-v2.json`另存，不覆盖人工修改。

助手逐屏复核句意、指代、完整问句、专名与单位，以及预期动作和阅读窗口，调整初切结果，不强制每屏相同字数。初切草稿保留生成依据；把复核后的各幕`captions`作为第2步画面时间表的唯一分屏来源，填写实际时间，不能在动画脚本再维护另一套文字数组。正式逐屏预览随后由时间表统一导出。初切与人工复核分别如实记录；从人工数组导出文件不等于运行过程序初切。

沿用既有内容和切分确认节点，向用户说明交付的是语义段、初切草稿还是已复核逐屏字幕。用户索要“字幕切分”时，交付每条对应一屏的文件；时间表尚未生成时可交付明确标注状态的初切草稿，不能只给正文段落预览。用户确认后，助手记录`content_approval: {"confirmed": true, "statement": "用户原话"}`；调整涉及改词、增删正文时，仍先按原要求确认，不增加审批节点。

内容与切分确认完成后执行一次版本绑定，此时不需要画面或时间表：

```bash
npm run timeline:vibe -- course/episodes/03-topic-slug/制作索引.json --bind-approved-source
```

命令先核对正式稿与预览，再保存`content_approval.source_sha256`，记录本次认可的各幕正文及切分版本；它不创建用户确认。原文或切分变化后，普通时间表、review和发布检查会拒绝旧绑定，须先按已有改稿确认流程处理再更新绑定，不能用此参数直接消除未确认改稿的报错。更新正文绑定会使旧的整片审片和发布确认失效；相同版本重复绑定保留已有确认。已确认的旧期次可在核实现存文本确为认可版本后补绑定，不重复索取未变化内容的确认。技术示例使用`example.technical_only`明确跳过真实正文确认绑定，不用它绕过正式制作检查。

这里绑定的切分版本是`split_preview`所指的语义预览。后续只调整逐屏断点、换行或时间且不改变正文及语义预览时，不重绑正文或重复索取内容确认；更新实际时间表、逐屏预览及受影响画面后，按原审片范围复核。

## 2. 全片统筹时间，再逐幕制作

先粗排全片的阅读、动作、揭示与停留时间，检查是否过长、重复或主题出现太晚；在已有时间表中标明首次主题登场的开始及完成时刻，使用相对正片0秒的累计时间，按[首次点题时间](motion_design.md#首次点题时间)核对后再逐幕实现并审看。四幕总时长是本期设计结果，不以每句字数、参考片重拍点或TTS读完速度机械决定。

场景、镜头和视觉阶段不设最短时长；额外时长限制只设上限，并按[时长与计时口径](motion_design.md#时长只设上限)在已有时间表说明约束对象及连续起止，不把换字幕或局部高亮当作重新计时。没有确认依据时不自行添加统一场景秒数阈值。

将已人工复核的初切草稿中各幕对象分别保存为画面时间表，填写实际`total_s`及每屏`start/end`，复核提示的处理理由留在已有记录中。时间未确定的`null`不能进入渲染。索引填写`acts[].visual_timing`，不是TTS timings；以下仅展示时间表结构，不是固定分屏模板：

```json
{
  "total_s": 8,
  "source_text": "这些投入收不回来。未来的时间还能选择。",
  "captions": [
    {"id": "c01", "start": 0, "end": 4, "text": "这些投入收不回来。"},
    {"id": "c02", "start": 4, "end": 8, "text": "未来的时间还能选择。", "emphasis": ["时间"]}
  ]
}
```

字幕必须能读完，时段不重叠且不超出本幕；拼接字幕去掉标点和空白后须与`source_text`一致。重点放在具体词上，只强调必要的词，每幕通常不超过三个，不要求每句着色。源码的`const DUR`和根`data-duration`与`total_s`一致。

时间表的`captions`应落实实际逐屏显示：先按保留标点的原文确定分屏，再填写各屏真实起止时间，最后显示时去标点；切分预览的一条可以对应多条时间表字幕，显示层按时间表逐屏切换。分屏顺序、单屏长度、双行条件和实际画面验收统一按[主字幕规范](motion_design.md#主字幕长度与分屏)执行，不把较长的讲解稿语义组直接当作必须整句同屏的字幕。

准备所有时间表后执行：

```bash
npm run timeline:vibe -- course/episodes/03-topic-slug/制作索引.json
```

命令对照已绑定的正式稿、语义预览与各幕`source_text`，校验字幕覆盖、时段及同屏最多24字，再从同一组`captions`生成连续的`整期时间表.json`与`逐屏字幕预览.json`，登记索引的`timeline_summary`、`caption_preview`和总时长。逐屏预览仍用`act1`等数组保存，每条恰好对应一屏，顺序、文字和标点与实际时间表一致；语义预览与逐屏预览必须使用不同文件路径。

时间或断点变化后重跑该命令，不手改导出的预览，也不沿用旧边界。review和发布检查会逐条核对已登记的逐屏预览，仅全文拼接相等但屏数或断点不同仍须重新导出。未登记该字段的历史索引保留兼容，重新制作时运行时间表入口即可补齐。字数和导出检查不代替每行长度、实际显示是否累计旧字、阅读时间与画面主次，具体按[字幕规范](motion_design.md#主字幕长度与分屏)执行。

## 3. 把画面设计成连续发生的过程

按[动态画面要求](motion_design.md)依次落实四层，不从固定布局直接开始堆局部动效：

| 层 | 要落实的事 | 使用已有产物 |
|---|---|---|
| [观看推进](motion_design.md#第一层观看推进) | 本段接住什么期待，产生什么发现或情绪变化，如何回应前文 | 观看主线、正文及内容审查记录 |
| [连续事件与对象关系](motion_design.md#第二层连续事件与对象关系) | 按讲解任务组织主体、范围与表达方式，连接触发、过程和结果；长段有持续发展 | 画面时间表、已有节拍说明 |
| [镜头与视觉重心](motion_design.md#第三层镜头与视觉重心) | 主次随事件变化，必要解释靠近主体、随动作出现；镜头兑现信息任务 | 时间表中的镜头与标注说明、实际画面源码 |
| [实际画面验收](visual_review.md) | 连续复查整幕和相邻接点，分别判断结构发展、动作解释、视觉表现及技术结果 | 实际片段、制作索引或已有验收记录 |

画面编排进入实现前，按[画面编排与持续发展](motion_design.md#画面编排与持续发展)连续核对相邻任务：谁接管主体、观看范围或关系怎样发展、结果如何引出下一段。仅在固定布局轮流加卡片、图标或高亮而未兑现任务变化时，退回编排；不能只因局部动作已写齐而放行。结尾按[结尾收束](motion_design.md#结尾收束)在同一时间表中说明承接状态、可见结果与最后构图的联系，再进入实现。字幕不变时也可以丰富对应动作，但不为填空增加无关动作。局部返工和复用前按第四层核对既有反馈与验收状态，保留有效部分及其他未解决项。

主题登场按[主题登场与特效选择](motion_design.md#主题登场与特效选择)结合本期知识点、具体旁白及前后画面设计，保留有效的呈现方式并加强揭示瞬间；不套用固定特效模板或复制已认可小样。点题后的纯展示停留、后续接续及选效依据统一按该节落实到已有时间表和实际审片。

制作时对照编排实现主体过程及任务接续，按[动作表现方法](motion_design.md#动作怎样产生表现力)安排起动、响应、速度和落定，并按[动作标注与解释](motion_design.md#动作标注与解释)让必要名称、数字和解释贴近对应主体、随动作同步。先核对实际源码的连续小样，包括任务转换、动作力度、标注移动中途和缩小状态；若只实现了局部动画而未实现组织变化，修实现或退回编排，不用新增装饰、切镜或运镜替代。

背景基调默认继承[深蓝或蓝绿暗底](motion_design.md#背景也参与表达)，本期各幕及后续各期直接沿用，不再每期重新询问浅色还是暗色；用户明确指定其他方向时再调整。其余配色、字体、形象、材质与运动感觉按本期内容设计，已有确认继续有效，新的视觉方向仍沿用既有风格确认节点及实际画面审看。Vibe不强制使用教学A/B/C固定开场或视频章节覆盖栏。各幕仍要共享视觉语言，具体环境随内容改变。

文字按已确认的[手机观看字号](motion_design.md#手机观看字号)制作：1920×1080基准下，主字幕80px，观众必须读清的场景文字至少64px；仅表现有字而无需阅读的细节可更小。编排时区分文字用途，实现及审片时检查阅读时段内缩放后的实际大小；空间不足先调整分屏、构图或必要双行，不缩字塞入。字体风格可随本期设计，字号标准直接沿用，不重复询问。

画面源保存在`course/acts/epNN_slug/`，索引填写`visual_source`、`visual_assets`及可选`sfx`。HTML使用现有HyperFrames契约：

- 根元素标明`data-composition-id="main"`、`data-start="0"`、画幅和时长。
- 单个暂停GSAP时间轴注册到`window.__timelines["main"]`，正向和反向定位一致。
- 放置唯一`/*__SUBS__*/`，用注入后的`SUBS`更新主字幕，文字层保持稳定阅读区。
- 使用本仓库字体路径；外置素材通过`visual_assets`进入构建，参考[技术示例](../../../examples/vibe-knowledge/README.md)。

动作声可以是单声道或立体声。没有动作声的分段让`sfx`为空，渲染器使用实际静音音轨完成拼接；它不是伪造配音，也不会填入`audio`或`timings`。有意裁切只声明最小局部元素，沿用布局、首现、解码和运动检查，不能豁免整幕。

```bash
npm run review -- course/episodes/03-topic-slug/制作索引.json --act 1 --check-only
npm run review -- course/episodes/03-topic-slug/制作索引.json --act 1 --range 0:6
npm run review -- course/episodes/03-topic-slug/制作索引.json --act 1
npm run review -- course/episodes/03-topic-slug/制作索引.json
```

Vibe审片直接输出high质量，浏览器GPU、NVENC、每幕2个worker、分幕串行；有效分幕沿用现有哈希缓存。局部预览不登记整幕完成，其他有效幕不用重渲染。每次交付对应视频、正式稿及索引`caption_preview`所指的逐屏字幕路径，注明版本与范围；需要解释正文结构时另给语义预览并标明用途。按用户安排逐幕审看，合并前检查全局起伏与所有幕间接点。

交付前按[Vibe实际画面验收](visual_review.md)连续复查整幕及相邻接点，并在正常速度、约360～480px宽的实际MP4中核对动作与解释能否同时看懂。结构停滞、任务变化或视觉表现未兑现、结尾结果未完成收束、必要标注遮挡或读不清时必须返工，具体起止和原因记入已有验收记录；技术检查通过或最新局部修好不能抵消这些失败，也不新增用户审批节点。

## 4. 固定背景音乐与混音

动作声对应具体可见动作，切镜头不自动加沙沙声。先选音色，再检查音量、落点和密度。音乐、人声与动作声分别处理；先完成无人声版本，可选人声在成片后再讨论。需要精确踩音乐时提前确定素材和片段，后加音乐不声称已经按音乐重拍制作。

Vibe系列固定使用《千年之后》氛围版试听音乐，项目内的固定本地路径为`.local/music/千年之后_氛围版_试听.mp3`。背景音乐增益固定为`0.25`（25%），动作声增益保持`1`（100%）；这是用户已确认的系列设置，后续每期直接沿用，不重复选曲或询问比例。用户明确要求更换音乐或调整比例时，才处理对应变更。

首次配置将这份音乐放入上述位置；该目录已被Git忽略，音乐不随仓库提交。文件缺失或损坏时明确报告并补齐同一素材，不静默换曲。音乐是背景配乐，不生成旁白人声，也不触发声音克隆。

音乐始终从正片0秒开始，随视频结束。先用`ffprobe`读取无BGM底片的实际时长：音乐够长时直接使用固定原文件；不够长时，从头循环同一首到覆盖底片全长，生成本期的循环音轨，不换曲、不留无配乐的尾段。例如在仓库根目录执行，替换底片、期次、版本及实测秒数：

```bash
ffprobe -v error -show_entries format=duration -of default=noprint_wrappers=1:nokey=1 "底片.mp4"
ffmpeg -hide_banner -y -stream_loop -1 \
  -i ".local/music/千年之后_氛围版_试听.mp3" \
  -t "底片实测时长秒数" -map 0:a:0 -vn \
  -c:a pcm_s16le -ar 48000 -ac 2 \
  "course/episodes/03-topic-slug/bgm-loop-vK.wav"
```

循环只是重复原音乐，不自动做淡入淡出、交叉淡化或归一化。准备后复核音轨时长、循环接点和全轨解码；底片变长后重新核对，不能沿用较短的旧循环文件。保留固定原音乐及已确认版本，循环产物按本期版本另存。

在制作索引填写已确认的系列默认设置；`bgm.file`在原音乐够长时指向固定文件，生成循环音轨后改填本期真实的循环文件路径。以下是正式默认值，不是待试听的候选比例：

```json
"bgm": {
  "file": ".local/music/千年之后_氛围版_试听.mp3",
  "source_gain": 1,
  "gain": 0.25,
  "approval": {
    "confirmed": true,
    "statement": "每次都是固定用这个。这个就是固定的背景音乐，就是不断重复，如果说他的背景音乐不够的话音量比例就是背景音乐25%。"
  }
}
```

已有系列确认可以沿用，不要求每期重新试听批准配乐；完整最终视频仍须按原审片节点确认。只有用户要求试听或调整时，才生成分轨试听页：

```bash
npm run preview:music -- course/episodes/03-topic-slug/制作索引.json
```

试听页引用未混音乐的`review_base_output`，避免双重叠加；暂停和拖动时音乐同步。先准备够长的原音乐或循环音轨，再打开试听。页面上的滑杆或上次浏览器保存值不自动改变正式索引；用户明确要求的新比例才更新对应设置。所有增益均为线性比例，不自动归一化、压低原声或加淡入淡出。

```bash
npm run mix -- course/episodes/03-topic-slug/制作索引.json
```

命令复制视频编码数据，另存配乐版并检查解码、声道、起止、时长和削波，保留底片与原音乐。先核验临时候选，通过后才替换输出；失败不覆盖已有配乐版。混音版更新`review_output`，需要审看这份完整最终视频；默认配乐未完成时，不将无BGM底片视为完整最终视频。

完整review始终写当前版本的无BGM底片，不把配乐路径当作画面输出。重建画面或改变混音后，旧发布验收状态失效；未变化的混音文件保留已有确认。已确认内容需要修改时另存新版本，复用未改动的媒体，再执行受影响阶段。

## 5. 独立封面与发布文案

进入本步读取[独立封面制作与验收](cover_workflow.md)：先确定中心主题及整张海报的视觉创意，再按实际能力选择AI生图或代码制图；缺少生图能力时直接代码生成。两条路径都交付项目内的实际3:4图片，说明采用方式与原因，完成审美和规格检查，再按已有节点取得用户确认。封面可以使用独立于正片内容的视觉表达，不强制搬用正文道具；详细设计、提示词、出图、保存与返工标准统一由该文档维护。

发布TXT仍包含标题、发布文案、标签、视频总结、视频章节，顺序与[发布交付](../common/release_delivery.md)一致。Vibe专属规则：

- 标题为`Vibe知识大赏｜主题词：短问题或反差`，冒号后含标点最多15个字符，通常10～12个汉字即可，不为凑长度加词。
- 正文简短展开同一个矛盾，结尾保留一个有力的问题，避免重复反问。只改发布文案不自动改讲解稿或视频。
- 标签包含`#Vibe知识大赏`及与主题相关的标签；不强制`#AI基础`或`#深度讲解`。
- 总结50～200个非空白字符，独立解释核心认识和必要边界，不照抄发布正文。
- 章节使用索引中的短标题，按正式整期时间表四舍五入到整秒，不提前估计。

## 6. 确认高清审片版，生成并验收发布包

完整最终视频获用户确认后，助手在`review_approval`保存`confirmed: true`、用户原话与该文件的SHA256。发布入口拒绝确认后变动的文件；示例例外只表示技术核验，不创建用户认可。

```bash
npm run publish:package -- course/episodes/03-topic-slug/制作索引.json
```

发布入口直接复制已确认的high审片版，将选定的独立封面复制为同目录`cover.png`，保留同版文案，并执行路线发布检查。它核对文件、版本、规格、时长、章节、文案、音轨一致、3:4封面和台账；不要求片尾静音或首帧嵌入封面。通过后保存`release-check.json`，真实登记`publish_bundle.complete`。

修改文案、封面或索引后独立复查：

```bash
npm run check:release -- course/episodes/03-topic-slug/制作索引.json
```

输出仍在`pipeline/output/course/epNN_slug/vK/`。公开上传须按用户授权另行执行，不把本地交付写成已公开发布。生成视频、用户声音、音乐、模型、密钥和个人路径继续本地忽略；生产规则和通用工具随仓库分发。
